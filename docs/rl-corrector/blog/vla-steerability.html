01 — The question

What we tested, and why we thought it would work

Robot policies fail, and mostly they fail silently — the arm does something confidently wrong and nobody finds out until the episode ends. We already had the first half of the fix: a calibrated uncertainty cascade that reliably flags "this episode is going bad." The obvious next question is what to do with that flag.

The premise was almost too clean. These are vision-language-action models. Language is a first-class input. So when the detector fires, hand the failure to a VLM that can actually see the scene, let it write one corrective instruction, feed that back to the policy, and score the result on whether the cube ended up in the tray. That last part is what makes it a real RL problem rather than a prompt-engineering exercise: the reward is verifiable. No judge model, no preference data — physics decides.

The three bets, stated plainly so they can be judged:

  1. The detector can find failures early enough to matter. Otherwise you are correcting a lost cause.
  2. Language moves the policy. If instructions don't change actions, there is nothing to optimise.
  3. A trained per-state corrector beats any fixed prompt. This is the part RL is for.

Bet 1 landed. Bet 3 never got a fair test, because bet 2 failed — and it failed in a way that turned out to be more interesting than success would have been.

02 — The short version

What we found

The entire apparatus works. A custom verifiers environment, a sim rollout server, a calibrated failure detector, and self-hosted vision GRPO on prime-rl all ran end to end and produced real weight updates on a real VLM. And the policy underneath was completely unmoved by anything the corrector said.

Confirmed working

The full loop: spike → failure report with frames → corrector emits an instruction → policy resumes → sim returns a verifiable reward → GRPO forms group-relative advantages → LoRA update. 66–100% of rollouts per step produced non-zero advantages.

Did not work

Learning. Reward sat at ≈ −0.149 across the 20-step shaping run and ≈ −0.058 across the 40-step vision run, and never climbed in either. The corrector converted zero failures. Probe the policy directly with contradictory instructions and its actions move by roughly 0.02° per joint — statistically indistinguishable from sending nothing at all.

The honest claim

It is tempting to write "VLAs aren't language-steerable." That over-claims, and we don't believe it. The defensible version is narrower and more useful: this VLA was trained in a regime where language was never load-bearing, so it learned to ignore language. One task, one embodiment, one fixed instruction string — vision alone fully determined the correct action at every single frame. There was never any gradient pressure to read the words.

We then did the thing you're supposed to do with a diagnosis: we tested it. We rebuilt the training data so the instruction changed within each episode (three sub-goal captions tracking the phase of the motion), tripled the dataset, and ran two finetunes — one with the language backbone frozen, one with LoRA on the VLM itself so the language layers could actually adapt. Both were negative. That failure is what sharpened the mechanism from a hunch into something specific, and it is covered in detail below.

03 — The build

How it actually works

Four moving parts. Three of them want a GPU; the one in the middle is deliberately weightless.

  │  vLLM: Qwen3-VL-4B   (GPU) │  instruction     │  MolmoAct2 VLA            (GPU)   │
  │  LoRA trainer        (GPU) │◄────┐      ┌────►│  MuJoCo SO-101 sim                │

  │   runs the ────┼── verifiers env │:8100 │     │  FastAPI /episode/{start,run,...} │
  └────────────────┼───────────┘     └──────┘     └───────────────────────────────────┘
                   └──── reward → group advantages → LoRA update

The vla-corrector environment carries no torch and no mujoco — it is a thin httpx client. That separation is the single best structural decision in the project: the heavy, fragile half (an 11 GB policy, a physics sim, EGL rendering) lives behind an HTTP boundary, so the RL side can be developed, tested and swapped without ever loading a robot model.

The corrector's job, as it sees it

The system prompt is deliberately blunt — we want a control signal, not an essay:

The reward

Success is the only term that means anything; the other two are shaping. Worth stating clearly, because it becomes important later: this is how the reward was designed, not an account of what drove learning. Nothing drove learning.

vla_corrector.pythe rubric
async def reward_success(*, state=None, **kwargs) -> float:
    """Verifiable reward: did the VLA place the cube in the tray?"""
    return 1.0 if (state and state.get("success")) else 0.0

async def reward_uq_reduction(*, state=None, **kwargs) -> float:
    """Shaping: did the corrections calm the uncertainty over the episode?"""
    tr = (state or {}).get("uq_trace", [])
    if len(tr) < 2: return 0.0
    return max(0.0, float(tr[0]["combined"]) - float(tr[-1]["combined"]))

funcs   = [reward_success, penalty_interventions]   # discourage over-correcting
weights = [1.0,            -0.05]
if shaping:
    funcs.append(reward_uq_reduction); weights.append(0.1)
rubric = vf.Rubric(funcs=funcs, weights=weights)

That −0.149 in the hero chart decodes exactly: success is 0, so reward ≈ −0.05 × 3 interventions + 0.1 × (an uncertainty drop of roughly nothing). The corrector was being scored almost entirely on the penalty for trying.

Turn structure

One turn equals one intervention. The environment always shows the model a failure before it is asked to act, so there is no wasted turn:

vla_corrector.pyMultiTurnEnv
async def setup_state(self, state):
    ep = await to_thread(self.client.start, info["seed"], info["cube_xy"], info["vla_task"])
    report = await to_thread(self.client.run, ep["episode_id"], self.max_frames)
    if report["status"] == "spike":                  # seed the failure into the prompt
        state["prompt"] += [_report_message(report, self.include_image)]
    else:
        state["final_env_response"] = _terminal_message(report)

async def env_response(self, messages, state, **kwargs):
    correction = _last_assistant_text(messages)
    await to_thread(self.client.correct, state["episode_id"], correction)
    report = await to_thread(self.client.run, state["episode_id"], self.max_frames)
    if report["status"] == "spike":
        return [_report_message(report, self.include_image)]   # another intervention
    state["final_env_response"] = _terminal_message(report)      # terminal → rollout ends
    return []

Training config

GRPO has no critic — the group mean is the baseline, which is why reward variance inside a group is life or death. Two settings below were hard-won and are called out in the debug notes: Qwen3-VL-4B (the 2B is absent from prime-rl's renderer map and would silently drop the images) and disabling enforced zero-advantage filtering (uniform all-fail groups otherwise crash the run outright).

The most portable lesson in the whole project

The finetune looked broken for two hours. Loss had converged beautifully; eval was 1/8 with zero grasps. We chased sim cadence, then execution horizon, then the image pipeline. The actual bug was found in two minutes by a teacher-forced check — feed a training frame back in and compare the predicted action to the known-correct one:

teacher-forced diagnosticthe smoking gun
MEAN ABS ERR per joint (deg): [ 0.73  38.19  91.98  0.00  0.00  5.50 ]
                                pan   lift   elbow  wristF wristR grip

Four joints near-perfect, two catastrophically wrong — and those two are exactly the joints carrying a sign flip and a +90° offset. The model was fine; the serving code was reading its output in the wrong frame. A converged loss only proves the model fits in its frame. Validate the action round-trip before you ever run closed-loop eval.

The failure detector

Three detectors, calibrated on successful runs: SMD (Mahalanobis distance on joint state), RND (vision novelty over SigLIP embeddings), ACE (spread across sampled action chunks). One of them does all the work.

RND — vision novelty1.00carries it and cheap: a SigLIP embed, not a VLM forward

Dropping ACE's sampling removed roughly 75% of per-frame compute at zero cost to separation. But note the number that should have worried us more at the time: mean lead time ~127 steps out of a 130-step episode. The detector fires at frame zero.

The signal path is genuinely proven — sim reward flowed into group-relative advantages into a 33,030,144-parameter LoRA update on a real VLM, driven by a physics-verifiable outcome. It just had nothing to learn, because the reward variance producing those advantages came from the shaping term, not from corrections changing outcomes. GRPO was optimising a proxy.

Probing the policy directly

So we stopped measuring the loop and measured the channel. Give the policy the same observation under contradictory instructions and see how far the action moves:

Steerability probe

≈ 0.02° of change per joint on the finetuned model (grand mean over four opposite pairs × four cube positions), ≈ 0.01° on base MolmoAct2 — for whole-task swaps as well as fine corrections — and 0.00–0.01° on the later caption-trained checkpoints, even on the model's own training captions. Not a weak signal — no signal. The corrector had nothing to steer with. Whatever it emitted, the arm did the same thing.

Testing the diagnosis: make language matter

If language went dead because the training instruction never varied, then varying it should revive it. We rebuilt the dataset with three sub-goal captions changing across each episode, grew it from 50 to 150 demos (fixing a data bug where the cube spawned inside the tray in about a third of demos), and ran two finetunes: action-expert-only, and LoRA-on-the-VLM so language layers could genuinely adapt. We audited the LoRA regex to confirm it really trains the language attention and MLP layers — a valid test, not an accidental no-op.

05 — The audit

What we got wrong, and what we'd defend

A negative result is only worth anything if you've been hard on it. Here is the case against our own conclusion, as completely as we can make it.

Design flaws that could have masked a real effect

  • The detector fires at frame zero. A 127-step lead on a 130-step episode means RND was almost certainly keying on the initial cube position — flagging hard episodes as OOD immediately, not detecting in-progress deterioration. For a system premised on "correct the failing trajectory," we were largely predicting difficulty and correcting from the start. That is a different experiment from the one we thought we were running.
  • Zero-variance groups by construction. GRPO's baseline is the group mean. Cube positions were sampled uniformly, so most groups were all-fail or all-succeed — either way, zero advantage. The frontier band where corrections could actually flip an outcome was barely sampled. A later profile found the policy was near-binary, with essentially one flippable cube position in the whole workspace.
  • The reward's variance was fake. What made 66–100% of rollouts "trainable" was the uncertainty-reduction shaping term, not success. We proved gradients flowed; we did not prove they pointed anywhere useful.
  • Spike timing. Corrections landed at the moment RND crossed threshold, which given the above was often before the policy had committed to anything correctable.
  • The Stage-2 prompt sweep over-persuaded us. Eight positions, differences of a single episode — procedural's "+12%" is one flipped rollout. We treated a one-episode swing at n=8 as evidence the channel was live. The later, more careful probe (~0.02°) suggests those flips were execution noise, not language. This is the same error the n=20 caption result nearly repeated.

Confounds we can't fully rule out

  • The base-model comparison is contaminated. Base MolmoAct2 is visually out of distribution on synthetic MuJoCo frames, so its flat steerability can't cleanly be blamed on the language channel — it may simply be lost. We cannot cleanly separate "finetuning killed language sensitivity" from "this model never had much on these pixels."
  • Label noise in the caption experiment. Roughly 22–48% of chunk boundaries carried mismatched caption/action labels — enough to blunt a real effect if one existed.
  • Unequal training. The comparison models saw 2.5 vs 7.6 epochs. Not apples to apples.
  • The joint-frame fix is empirical. We patch j1 and j2 at serving time rather than rebuilding the dataset in the model's own frame. It works, but it's a correction layered on a convention mismatch, and it makes us less certain than we'd like about everything downstream.
  • Everything is one task, one embodiment, one simulator. Whether this generalises past SO-101 pick-and-place in MuJoCo is genuinely unknown.
  • Calibration AUC of 1.00 is in-sample and small-N (10 successes, 6 failures). It will soften on held-out data. We report it because it's what we measured, not because we think the detector is perfect.

What we'd do the same way again

  • The teacher-forced round-trip check — it turned a two-hour mystery into a two-minute diagnosis.
  • Putting the sim and policy behind an HTTP boundary, so the RL environment stayed testable on a laptop.
  • Auditing the LoRA target regex before trusting a negative result from it.
  • Killing the n=20 result by running it to n=60 instead of writing it up.
  • Keeping a running log of every dead end — most of this post came directly out of it.
  • Doing the whole thing for under $20 of rented GPU by renting per-hour and terminating aggressively. That covers the rl-corrector pods only — the finetunes, calibration recordings, probes, GRPO runs and the phase-caption follow-up — recorded per round from the provider dashboard. No billing export was retained, so these are readings, not receipts; the itemisation is in RESULTS.md, which is the single accounting for this work.
06 — Conclusions

What we think is actually going on

The best explanation we've found comes from Tedrake et al.'s Large Behavior Models work, and it predicts our result almost exactly.

They report that filtering out low-motion frames helps task-specific finetuning but hurts language conditioning. Their proposed reason: low-motion frames cluster at episode starts, and the start is precisely where the scene is most ambiguous — where several tasks share a similar opening image and the model is forced to read the instruction to choose a first action. Delete those frames and what remains are mid-trajectory frames where vision and proprioception already reveal intent. Language becomes redundant, and the model learns to ignore it.

Our case is a stronger version of the same thing

We finetuned on one task, one embodiment, one instruction string. Vision fully determined the correct action at every frame, not just the middle ones. There was no point in the training distribution where reading the instruction reduced loss. Language conditioning is learned only where vision is ambiguous — and we removed all the ambiguity. The corrector was speaking into a channel with no gradient behind it.

This also explains why the caption fix failed. Varying instructions over time doesn't help, because each caption's time window still maps to a unique, fully vision-determined state — the caption is redundant with what the camera already shows. Temporal variation isn't ambiguity.

The hypothesis we'd test next

To make language load-bearing you need states where the same observation implies different correct actions depending on the words. The cleanest version we've designed but not yet run: two placement targets. Identical cube position, identical scene — but the instruction names which tray. Vision cannot resolve it. The model must read the instruction or it cannot exceed chance. Alongside that: keep the low-motion episode-start frames, and only then add phrasing diversity for generalisation.

The pivot: steer the channel the policy already attends to

Making language load-bearing means an expensive multi-task retrain. There's a more direct route, suggested by someone who reported measurable success with it: Q-guidance. Train Q(vision_tokens, action) offline on labelled rollouts, then at inference sample actions from the VLA and bias toward high Q — best-of-N re-ranking, or gradient guidance, the flow-policy analog of classifier guidance. It intervenes in action space, reading the same vision tokens the policy actually uses, and sidesteps the language bottleneck entirely.

Most of what we built survives that pivot:

  • Carries over: the sim, the rollout server, reward labelling, and the uncertainty detector — which becomes the gate deciding when guidance is applied at all.
  • Carries over: Prime Intellect pods. A Q-network is ordinary PyTorch.
  • Does not carry over: prime-rl itself. It's GRPO over token log-probs for token-emitting policies; Q-guidance is value-based RL on a continuous action head. That's a trainer we'd write ourselves on Prime's compute.

Which leaves the open question we'd most like answered: is value-based or continuous-control RL in scope for the Prime stack? Everything else about the platform fit this experiment well — per-hour pods across providers, prime-rl handling vision GRPO with LoRA on a 4B VLM without complaint, and verifiers being flexible enough that our environment was a thin HTTP client over a physics sim. The gap is policies whose actions are numbers rather than tokens, which is most of robotics.

If you take one thing

Before building a correction loop on top of a VLA, spend an afternoon measuring whether the policy responds to language at all. Feed it opposite instructions on identical observations and measure the action delta. If it's ~0°, no amount of RL machinery above it will help — and we'd have learned that in an afternoon instead of at the end of a full GRPO run.

Two infrastructure notes that cost us real time

Use two disjoint GPUs and the combined rl entrypoint. We tried hand-splitting orchestrator and trainer onto one card. The trainer starts, loads the model, reports its LoRA parameter count — then hangs forever waiting for a run registration that only the combined launcher performs. Meanwhile the orchestrator keeps logging plausible Step N | Trainable 4/4 lines, because those are computed orchestrator-side. It looks like it's training. The weights directory stays empty. Verify a real training step, not the step counter.

Calibration artifacts are pipeline-specific. Our stored detector was fit on 2880-dim embeddings; a transformers upgrade changed the pipeline to 1536-dim. Every rollout 500'd. Re-fit calibration whenever the embedding pipeline moves.
